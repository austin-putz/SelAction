# Plan: Online Documentation System for SelAction

## 1. Goal

Stand up a proper online documentation site (something in the spirit of `pkgdown` for R, or `docs.rs`/ReadTheDocs for other ecosystems) that hosts **two distinct manuals**:

1. **User Manual** — how to install, compile, and run SelAction. Starts with Linux (Ubuntu), with Mac and Windows sections added later once `fortran_mac/` is fixed and a `fortran_windows/` exists.
2. **Technical/Methods Manual** — the exact mathematics as *actually implemented* in the Fortran source (not just the general theory from the original 2001 paper/manual), tied to specific modules, subroutines, and — where it matters for correctness — line numbers.

This plan covers tooling choice, information architecture, repo layout, migration of existing content (`manual/`, `docs/`), and a phased rollout. It does not implement anything yet — it's a plan to review before work starts.

## 2. Current State

- `manual/SelAction_Manual.md` (1128 lines) — the original 2001 manual, written entirely around the **Windows GUI** (`SelAction.exe`, click-through windows for Traits/Population/Groups/Index/Correlations). This GUI does not exist in `fortran_linux/`; the current programs (`mssel`, `msseld`, `msselo`) are CLI binaries driven by text input files. This manual is not usable as-is for the new user guide — it needs a structural rewrite, not a port.
- `manual/SelAction_Program_Description.md` (88 lines) — short, general description of the underlying selection index / inbreeding theory. Useful background source for the technical manual, but not implementation-level.
- `docs/*.tex` — four LaTeX reports (`SelAction_Technical_Report.tex`, `seldiscrete_report.tex`, `selinbreeding_report.tex`, `selovlp_report.tex`). Three are empty (0 lines); only `seldiscrete_report.tex` has real content (57 lines, covering `sel1s` only, generated by Gemini, no cross-links to source line numbers). This is the aborted attempt referenced in your message — LaTeX-per-module is a reasonable content shape but a poor *delivery* mechanism here: no search, no navigation between modules, no linking from an equation to the exact Fortran lines that implement it, PDF-only, and each module lived in an isolated file with no shared structure enforcing consistency.
- No static-site tooling exists anywhere in the repo (no `mkdocs.yml`, no Sphinx `conf.py`, no `_config.yml`, no CI docs workflow).
- Repo is public on GitHub (`github.com/austin-putz/SelAction`), so GitHub Pages is free and simple — no separate hosting decision needed.
- `README_Inputs.md` already does field-by-field input documentation reasonably well and should feed the technical manual rather than be duplicated.

## 3. Tooling Recommendation

### Primary: MkDocs + Material theme

**Recommendation: [MkDocs](https://www.mkdocs.org/) with the [Material for MkDocs](https://squidfunk.github.io/mkdocs-material/) theme**, deployed to GitHub Pages via GitHub Actions.

Why this is the closest thing to "pkgdown for a Fortran package":

- **Markdown-native.** `manual/*.md` is already Markdown — the user manual rewrite starts from a format you don't have to convert out of.
- **Math support.** Material's `pymdownx.arithmatex` extension + MathJax renders LaTeX-style `$...$` / `$$...$$` equations directly in Markdown. This replaces the abandoned `docs/*.tex` approach without losing equation quality — you can write `\mathbf{b} = \mathbf{P}^{-1}\mathbf{Gv}` inline in a `.md` file instead of a standalone `.tex` document.
- **Real navigation + search.** Built-in full-text search, a nav sidebar, and tabs — the thing a pile of static PDFs fundamentally can't give you. A reader can search "dFmtblup" and land directly on the right page.
- **Two-manual structure is a first-class feature.** Material's "tabs" navigation (`nav` sections in `mkdocs.yml`) map cleanly onto "User Guide" vs "Technical Reference" as two top-level tabs of one site, not two disconnected documents.
- **Low operational cost.** Pure Python + pip install, builds to static HTML, deploys via `mkdocs gh-deploy` or a one-file GitHub Actions workflow. No Ruby/Jekyll toolchain, no Node build pipeline.
- **Widely used for exactly this kind of project** — numerous scientific/simulation codebases (including several Fortran and C++ scientific computing projects) use MkDocs Material for user + theory manuals.

### Complementary: FORD for auto-generated API reference

**[FORD](https://forddocs.readthedocs.io/) (FORtran Documenter)** is the actual Fortran-specific equivalent of a `pkgdown` reference index / Doxygen — it parses `.f90` source directly and generates a browsable cross-reference of every module, subroutine, function, argument, and call graph, driven by specially-formatted comments (`!!`) you'd progressively add to the source.

Recommend adding this **after** the hand-written manuals exist, as a third nav item ("API Reference"), not instead of them:

- FORD is good at "what are the arguments to `sel2s`, what does it call, what calls it" — mechanical source-level facts.
- FORD is *not* a substitute for the technical manual's job of explaining *why* `dFmtblup` computes what it computes, or walking through the derivation behind an equation. That has to be hand-written and reviewed by someone who understands the quantitative genetics.
- Low cost to add later: `pip install ford`, one `.md` project file, `ford project.md` generates the site, can be linked into or embedded alongside the MkDocs site.

### Alternatives considered, not recommended (for now)

| Option | Verdict |
|---|---|
| **Sphinx** (+ MyST for Markdown) | Viable, has good math support (same MathJax), but heavier to configure than MkDocs for a project this size, and its natural habitat (autodoc from docstrings) doesn't apply to Fortran. Reconsider only if you later want Sphinx's cross-reference/citation machinery specifically. |
| **Quarto** | Strong fit *content-wise* (great math + citation rendering, could also emit a PDF from the same source), and worth a second look if formal citation management becomes important. Steeper toolchain (separate Quarto CLI binary, less common as a long-lived doc site vs. one-off reports). Not recommended as the primary tool, but flagged as the best alternative if MkDocs math rendering ever feels limiting. |
| **Doxygen** | Can parse Fortran but the output/UX is dated and C++-flavored; FORD is a better-fitting, purpose-built alternative for the same job. |
| **Stay with LaTeX in `docs/`** | This is what was tried and abandoned — no navigation, no search, PDF-only, hard to keep multiple module reports consistent with each other. Don't continue down this path as the primary delivery format; the underlying LaTeX/math *content* already started (`seldiscrete_report.tex`) can be ported into the new Markdown pages rather than thrown away. |
| **GitHub Wiki** | Rejected — not version-controlled alongside code review (PRs), weaker math/theme support, easy to drift from the actual source. |

## 4. Proposed Site Structure

One MkDocs site, two top-level nav sections (Material "tabs"):

```
SelAction docs site
├── Home                         (landing page: what SelAction is, quick links)
├── User Guide                   ← Document 1
│   ├── Installation (Linux/Ubuntu)
│   ├── Compiling from source
│   ├── Quick Start (run test1 fixture end-to-end)
│   ├── Input File Reference     (absorbs/links README_Inputs.md)
│   ├── Choosing a program (mssel vs msseld vs msselo)
│   ├── Output File Reference
│   ├── Worked Examples          (from examples/)
│   ├── Troubleshooting
│   └── macOS / Windows          (stub pages, marked "not yet supported", filled in later)
├── Technical Reference          ← Document 2
│   ├── Overview & module map    (mirrors "Module Dependencies" in CLAUDE.md)
│   ├── seltools.f90             (gcef, sabf, sintvi, rawl3, dutt*)
│   ├── selparameters.f90        (global parameters/state)
│   ├── selroutines.f90          (invrt, trunc, selection_index, matrix ops)
│   ├── seldiscrete.f90          (sel1s, sel2s, sel3s — ports seldiscrete_report.tex content)
│   ├── selovlp.f90              (ovlp, overlapping-generations math)
│   ├── selinbreeding.f90        (dFmtblup, BLUP-based inbreeding)
│   └── Known deviations/fixes vs. fortran_orig  (the bugfixes already documented in CLAUDE.md — segfaults, uninitialized reads — belong here so a reader validating output against the original knows what changed and why)
├── API Reference                (FORD output, added in a later phase)
└── Changelog / Citation
```

Each Technical Reference module page should follow one consistent template: theory summary → equation(s) with MathJax → **direct pointer to the Fortran subroutine/function and file** implementing it → any known numerical caveats (there are already several documented in `CLAUDE.md`, e.g. the `selovlp.f90` allocation-order bug, the `selroutines.f90` uninitialized-array bug) so the math manual and the "what got fixed" knowledge don't live in two disconnected places.

## 5. Repo Layout & Deployment

- New directory `docsite/` at repo root holds the MkDocs *source* (`mkdocs.yml` config, `docsite/index.md`, `docsite/user-guide/*.md`, `docsite/technical/*.md`). Deliberately **not** named `docs/`, to avoid colliding with the existing `docs/` (LaTeX technical reports) — those stay put as downloadable/reference source material and get linked from the new Technical Reference pages, not deleted.
- `manual/` stays as-is, untouched — it's the historical record of the original 2001 Windows GUI manual. The new User Guide supersedes it going forward but doesn't erase it (same "never modify `fortran_orig/`" spirit: it's a reference artifact).
- Deploy via a GitHub Actions workflow (`.github/workflows/docs.yml`) that runs `mkdocs gh-deploy --force` on every push to `main` that touches `docsite/**`, publishing to the `gh-pages` branch → served at `https://austin-putz.github.io/SelAction/`. This is the same mechanism the existing `TODO` about wiring `tests/run_tests.sh` into GitHub Actions already anticipates (CLAUDE.md notes CI doesn't exist yet) — worth setting both up together rather than two separate CI efforts.
- No versioning tool (`mike`) needed yet — single "latest" site is fine until there's an actual tagged release cycle.

## 6. Phased Rollout

**Phase 0 — Scaffolding**
- `pip install mkdocs-material`, initialize `docsite/`, minimal `mkdocs.yml` with the nav skeleton above, empty stub pages.
- GitHub Actions workflow to build + deploy on push to `main`.
- Confirm `https://austin-putz.github.io/SelAction/` renders.

**Phase 1 — User Guide (Document 1), Linux only**
- Write Installation + Compiling pages directly from CLAUDE.md's verified `gfortran` build commands (already correct and tested — this is a rewrite target, not new research).
- Quick Start page: walk through `tests/fixtures/test1` end-to-end (input file → compile → run → read output), since it's already a known-good fixture.
- Input/Output reference pages, pulling from `README_Inputs.md` (link or absorb — decide during implementation whether `README_Inputs.md` becomes a thin pointer to the site or stays the canonical source).
- Explicit "macOS / Windows: not yet supported" stub, matching CLAUDE.md's current honesty about `fortran_mac/` being broken.

**Phase 2 — Technical Reference (Document 2)**
- Port `docs/seldiscrete_report.tex`'s existing `sel1s` content into `docsite/technical/seldiscrete.md` as the template/pilot page (proves the LaTeX→MathJax math conversion works before doing the rest).
- Write the remaining module pages (`selovlp`, `selinbreeding`, `selroutines`, `seltools`, `selparameters`) from scratch, reading the actual `.f90` source for each — this is the bulk of the writing effort and should be done module-by-module, verified against real subroutine behavior rather than the 2001 paper's general theory alone.
- Add the "Known deviations/fixes" page consolidating the bugfix knowledge already written into CLAUDE.md.

**Phase 3 — API Reference (FORD)**
- Add FORD, generate the source-level cross-reference, link it in as the third nav tab.

**Phase 4 — Polish & wire-up**
- Add a docs badge/link to `README.md` (alongside the future CI badge from the existing TODO).
- Cross-link from `README.md`'s existing sections (Installation, Mathematical Background) to the new site rather than duplicating content in two places.

**Phase 5 — Later (not now)**
- macOS user guide, once `fortran_mac/` is actually fixed.
- Windows user guide, once a `fortran_windows/` build exists.
- Consider `mike` versioning if/when tagged releases start.
